# NovelGlyph Web v1.2.2 — 三模型 OCR 证据 × 全书字形归组

本版从 **v1.1** 原样保留手动框字全书像素重合、物理分列、逐字候选发现、字形组、Ruby 风险标注、边界拆分／合并、墨迹覆盖账本、人工 Unicode 审校以及 TXT/JSON 草稿导出，并新增独立的 **OCR 证据交叉审核** 模块。

**重要**：网页本身没有内置 Hayai、NDLOCR-Lite 或 48px 的权重，也不在前端运行 OCR。它读取这些模型或其他 OCR 程序**已经生成的单字文本＋原图像素坐标**，与物理候选匹配，提供人工复核排序。无法直接把任意 OCR 的整页／整列文本当作带字位的 JSON 使用。OCR 不会自动批准字形组、不直接写进已确认正文。即使三个 OCR 模型一致，也可能一起认错。

## v1.2.2 整本书工作区改进（2026-11-04）

- 将已压缩的原图 PNG 以 ZIP STORE 方式保存，避免再次逐页 DEFLATE 压缩导致整书保存长时间无响应。
- 新增独立入口「恢复已有工作区 ZIP（免重新扫描）」，与普通书页 ZIP 导入区分开。
- 恢复工作区使用 `manifest.pageFiles` 保存的**原始文件名**，防止每次保存/恢复都追加 `00001_` 前缀而使页名逐步漂移。历史工作区仍可恢复。
- 项目导入时增加书页数一致性、单页/总图像解压大小保护；恢复期间会显示加载进度。保存工作区按钮在打包期间禁用，阻止误触发并行导出。
- 不在 GitHub 存放小说原图、人工工作区、OCR 权重。用户在本地浏览器自行选择扫描 ZIP 或已有工作区 ZIP。

### 快速体验 407 页的正确方式

1. 从此前独立交付的私有文件中下载 `NovelGlyph_勇者01_407页_预扫描工作区_未人工赋字.zip`，不要将此数据上传至公开 GitHub 仓库。
2. 打开本网站，选择「恢复已有工作区 ZIP（免重新扫描）」，等待界面显示 407 页；进入「全书字位库」。
3. 按字形组核查原图，手动确认单字、校正边界；未知字符仍用占位符，OCR 一致仅作为建议。
4. 点击「保存工作区」备份包含原始书页与当前审核状态的 ZIP。恢复时继续使用专门的工作区导入入口。

**测试边界：** 407 页扫描结果来自既有本地工作区，不代表每个物理候选都是正确的单字，也不代表已经完成文字识别。

## 部署

将 `NovelGlyph_Web_v1.2_OCR字形交叉审核_GitHubPages_20261103.zip` 中的内容解压至静态网站根目录，即可通过 `index.html` 使用。亦可本地运行 `python3 -m http.server 8000`，再访问 http://localhost:8000 。演示素材和 JSZip 已随包提供。真实扫描源图及 OCR 文件都在本机浏览器读取，不经服务器上传。

## 使用步骤

1. 导入整书图片 ZIP/CBZ，点击「全书字位库」→「遍历整书发现候选字位」。这个步骤用投影法产生候选位置，不保证每段恰好一个字。
2. 准备单字坐标 OCR 文件，每个模型一个 JSON，`source` 使用不同值：例如 `Hayai`、`NDLOCR-Lite`、`48px`。点击「导入 OCR 单字坐标 JSON」多选导入。
3. 系统仅用原图像素坐标匹配；某个 OCR 单字矩形与候选字位的 IoU 必须不低于 0.60，且不能同时与多个候选产生相近分数。不能匹配的 OCR 条目会统计为「无匹配／歧义」，不会猜测坐标。
4. 「优先核对的形状组」先展示 OCR 异码冲突、人工确认冲突，再展示跨页多模型一致的候选组。点一个组仅将候选字符填进人工审核输入框，并**取消勾选批准状态**，必须看原图后主动确认。
5. 为避免误传播：如某个已批准的字形组，任何位置出现与组标签不同的人工确认，整组其他尚未逐位置确认的位置会暂时显示 `□`，状态为 `group_conflict_hold`。若两个不同 OCR 来源在同一位置高置信度地一致否认组标签，也会触发同样的安全停用；人工逐位置 Unicode 保留。
6. 对误切、重叠字形、Ruby、同形异码逐位置处理；可撤销 OCR 证据或重新导入某一来源。保存「项目 ZIP」会保留 OCR 证据，恢复时可继续审核。
7. 通过「导出 OCR-形状冲突报告」保存 `NovelGlyph-Hybrid-Audit-v1` JSON，用于与现有 Novel-formatter 裁决流程对照。

## OCR JSON 格式

UTF-8 文本，**每个位置是一个 Unicode 字素和一个原图像素框**。`page` 从零开始，`rect` 是 `[左,上,右,下]`，不接受相对于缩放预览图或已裁剪列图的坐标。

```json
{
  "format": "NovelGlyph-OCR-Evidence-v1",
  "source": "Hayai",
  "coordinate_system": "original_image_pixels",
  "page_index_base": 0,
  "items": [
    {"page": 0, "rect": [100, 200, 129, 231], "unicode": "の", "confidence": 0.96},
    {"page": 0, "rect": [100, 240, 129, 271], "unicode": "本", "confidence": 0.91}
  ]
}
```

按**完整来源**导入：同一 `source` 的新 JSON 会整体替换旧证据，避免重复计票。如果文件按分页拆开，请先在外部合并这些页，或使用 `source` 的分片后缀（注意不同分片不应视为独立模型，不能据此伪造多模型一致）。一个来源为同一个物理位置输出多条记录时，该位置此来源不参与投票。单次最多 30 万条，错误记录被统计剔除。

> 当前不支持直接导入 Novel-formatter 未带逐字原图坐标的整列 OCR 文本；其对齐必须先有正确且可验证的字符→字位关系。不能仅凭字符数或列顺序强行写回。

## v1.2 安全策略

- OCR 只投票、建议、警示；不可直接作为人工确认 `occurrence.verified`。人工核验的实际 Unicode 优先级最高。
- 跨位置候选必须来自至少两个不同 OCR 来源、两个独立物理位置和至少两个不同页面，且没有高置信度分歧或人工冲突，才有组级审核建议。仍需要人批准。
- Ruby/编辑过边界/非正文的字位不计入安全建议的可传播位置。`力/カ`、`一/ー` 等同形异码不进入自动批量建议。
- `已匹配`、`OCR一致`、`形状相同`、`人工批准` 是不同概念；报告将四者分开呈现。没有基于整本真实轻小说的可靠错误率测定，不宣传“超越 OCR”。

## 本次量化验收：原创排版、合成 OCR，不是真实 OCR 结果

使用 `tests/build_ground_truth_fixture.py` 生成 **8 页、2,208 个有真实 Unicode 和像素级位置标注**的原创日文样式排版样本，在此基础上运行 `tests/benchmark_hybrid.cjs`。OCR 的错误是程序按固定随机种子合成的，**没有运行 Hayai、NDLOCR-Lite、48px 模型**。

| 指标 | 原创无压缩图 | 同一素材 JPEG 55 质量再次解码 |
|---|---:|---:|
| 已知真实字位数 | 2,208 | 2,208 |
| 投影产生候选区段 | 2,314 | 2,326 |
| 能与真值一对一配准的真实字位 | 2,185 (98.96%) | 2,182 (98.82%) |
| 精确字形组数量 | 127 | 1,419 |
| 已匹配字位中加权形状组纯度 | 100% | 100% |
| 三模型模拟一致且无已知分歧的审核建议组 | 25 | 162 |
| 建议覆盖的正确匹配字位 | 200 | 497 |
| 建议对上述真值字位的准确度 | 200/200 | 497/497 |

**极重要的限定**：最后一行是从非常保守的、选择性输出的建议里计算的**模拟建议精确率**，并非整书识别正确率、OCR 模型的真实表现或人工审核省时实测。所列形状组纯度仅统计可以与真值一对一映射的区段，不覆盖错误拆分、Ruby、真实印刷变体和非正文。相比之下，1,419 vs 127 展示了 **精确位图归组对 JPEG 失真异常脆弱**。误切增加的区段不能算作正确识别。

此外，`tests/test_hybrid.cjs` 明确构造了「两个 OCR 模型一致认错」的情形，系统产生了**错误的待审建议**，但仍保持 **0 个未审批写回**。这个测试证明的是写回保护，不是 OCR 的语义正确性。

## 复现

```bash
for t in tests/test_*.cjs; do node "$t"; done
python tests/build_ground_truth_fixture.py
node tests/benchmark_hybrid.cjs clean
node tests/benchmark_hybrid.cjs jpeg55
python tests/browser_hybrid_e2e.py
```

生成 JPEG55 输入的准备脚本已经包含在 `tests/make_jpeg_variant.py`，请先运行后再跑 JPEG55 benchmark。Chromium 浏览器测试采用同源 Worker 的安全注入路径（当前执行容器限制本地 HTTP 浏览器导航），不能代表真实 GitHub Pages 已经发布验证。

**真实 407 页扫描不在此包中，v1.2 未做真实 407 页新验收；没有进行 Novel-formatter 实际 OCR 模型性能对比。** 后续首要任务是从 Novel-formatter 导出带可验证原图坐标的 OCR 证据，再用有真实标准答案的扫描页比较最终字准、误传播和人工耗时。
